## Scope and data model

- 2026-10-06 · Account, invite, password, session and household operations are never AI tools; the tool registry and `/mcp` start in M1. (Confirmed)
- 2026-10-06 · Change records carry a fifth client value, `cli`, for admin commands. (Confirmed)
- 2026-10-06 · Password reset by email ships in M0 when SMTP is configured; without SMTP the admin command is the only path. (Confirmed)
- 2026-10-06 · New domain entities approved at kickoff, each built in its milestone: Favourite and DayTypeOverride (M1), Store and ListTextMemory (M2), StockStatus (M4). (Confirmed)
- 2026-10-06 · Item category is a fixed enum with translation keys, not a table.
- 2026-10-06 · Two invite kinds: `household` (issued by the admin command, creates a new household on acceptance) and `partner` (issued by a member, joins their household).
- 2026-10-06 · Invites are single use, expire after 7 days, and carry both a link token and an 8-character code; both are stored hashed.
- 2026-10-06 · An instance admin is a user with `is_admin`; admin powers exist only in the CLI, there is no admin UI.
- 2026-10-06 · Primary keys are UUIDv7 generated by the app, so clients can create ids for offline use later.
- 2026-10-06 · Language and time zone live on User (as in the brief); visibility toggles, start screen and push switch live on Profile.
- 2026-10-06 · Supported time zones are IANA names; the default is `Europe/Berlin`.
- 2026-10-06 · Any member can rename the household; the name defaults to the first member's name.
- 2026-10-06 · The "open on Today or List" choice is stored on the profile now; its switch appears in M2 together with the list.
- 2026-10-06 · Sessions, login attempts, reset tokens and jobs are infrastructure rows: no change records; they are purged hourly once expired.
- 2026-10-06 · Generic foods: 248 items selected from BLS 4.0 plus one estimated whey protein entry (brief: about 300); values per 100 g, base unit g for every BLS item, servings only where the BLS appendix gives them. The selection lives in `backend/seed/` and is rebuilt with `backend/scripts/build_bls_seed.py`.
- 2026-10-06 · The first admin gets 31 staple foods as favourites; everyone else starts with none.
- 2026-10-06 · Search score: trigram similarity, plus up to 0.3 for use in the last 90 days, 0.15 for a favourite, 0.2 for the household's own items; an empty query shows favourites and recent foods.
- 2026-10-06 · Entries on a future date are planned (at most 30 days ahead); today and past dates are logged. So `log_planned_meal` ships in M1 as the same call with a future date.
- 2026-10-06 · Saved meals are recipes with one serving and use the recipe tool names (`list_recipes`, `create_recipe`, ...); logging one copies its ingredients, so later edits do not change past days.
- 2026-10-06 · A quick add needs a name and kcal; missing macros mark that day's totals as incomplete instead of counting as zero.
- 2026-10-06 · Copying a meal (own or the partner's) or a whole day creates new entries for the person copying; the target day decides planned or logged.
- 2026-10-06 · Week pattern: seven letters T/R starting Monday, default all rest days (`RRRRRRR`) until the person sets it; a single day can be overridden from the day view.
- 2026-10-06 · Targets are versioned by `valid_from`; earlier days keep the targets they had. With no targets the day shows totals only.
- 2026-10-06 · Extra tools beyond the brief's list, each a thin call to an existing service: `get_targets`, `set_targets`, `set_day_type`, `copy_meals`, `set_favourite`, `lookup_barcode`, `search_online`, `delete_recipe`.
- 2026-10-06 · Shopping list items carry a client-made UUIDv7 id, a time per field and a tombstone: adds are idempotent by id, each field is last-write-wins by the time the change was made (a phone clock ahead of the server counts as now), and a removed item stays removed. No separate idempotency-key table is needed because every operation is idempotent by construction.
- 2026-10-06 · Quantity on the list is free text ("2", "500 g", "1 Pck"); one-field adding splits a leading or trailing quantity off the text on the server. M4 turns quantities into amounts when 'Bought' is confirmed.
- 2026-10-06 · Stores: eight built-in rows (ALDI, Lidl, EDEKA, REWE, Netto, Penny, dm, other) with stable ids and untranslated brand names, plus custom stores per household. An item's default store is the store the household last used for it (list memory), not a field on the item, because generic items are shared and read-only.
- 2026-10-06 · ListTextMemory is the table `list_memory`: per household and per catalogue item or normalized text, the last aisle and store and a use count. It powers history suggestions and remembers the aisle a free-text item was moved to.
- 2026-10-06 · Checked items stay on the list until 'Remove checked' (M2) or 'Bought' (M4); checked items sink to the bottom, newest first.
- 2026-10-06 · Undo on the list covers the last check and the last removal (removal is undone by adding the items again under new ids, since removal is final).
- 2026-10-06 · The 'open on Today or List' switch is in Settings; it applies to the first screen of each app launch.
- 2026-10-06 · Extra list tool beyond the brief: `update_list_items` (text, quantity, store, aisle). Tools name stores by name or key instead of id.
- 2026-10-07 · M3 adds no core entity beyond the brief's Offer. Weighed amounts ("exact amounts per component can override the share") are a detail table of the meal participant, `meal_exact_amount` (participant, component, grams eaten); it goes with either. Please confirm.
- 2026-10-07 · Recipes and saved meals are one table, one service and one API (`/api/recipes`, `kind` recipe or saved_meal; a saved meal is always one serving). The M1 saved-meal routes, `saved_meal_*` error codes and the `saved_meal_id` field are replaced by `recipe_id`; the recipe tools take `kind` and `staples_only`.
- 2026-10-07 · A plan is an entry whose parts are `planned`. `log_food` keeps the M1 rule (a future day is planned, today and the past are eaten); `plan_meal` (API `plan: true`) always plans, for today up to 30 days ahead, so tonight's dinner can be planned too. On the add screen a switch "only plan it" appears for today.
- 2026-10-07 · A plan may be just a name: it becomes a free-text component without numbers, and the day counts its kcal as incomplete (never as zero) until it is eaten and filled in. Logging a food still needs kcal. Moving a meal to a future day makes it a plan.
- 2026-10-07 · A joint meal is one entry with a part per person; `joint` at creation shares it with everyone else in the household, evenly (half and half for two). "Eaten" by one person logs everyone's planned part (skipped parts stay skipped); putting a part back to planned or skipped changes only one's own. Day, slot, time and foods of a joint meal are the dish's, so changing them changes them for everyone on it.
- 2026-10-07 · Shares: 5 % to 95 % on a joint meal. Setting my share sets the others' planned shares to the rest (in proportion to what they had, when there are more than two); an eaten part is never changed behind its owner. When someone leaves a joint meal, those still planned take over the dish.
- 2026-10-07 · A weighed amount is the grams the person ate of one item component; their intake for that component is that amount over the dish's, instead of the share. Components keep their rows when an entry is edited as long as their item stays, so changing a time does not lose weighed amounts. Quick-add components cannot be weighed.
- 2026-10-07 · Offers: the sender offers their own planned meal for today or later; `share` is the receiver's share (default 50 %). Accepting adds the receiver to that entry and replaces their own planned entries in the slot (eaten and skipped ones stay; a snack replaces nothing, since there can be several). A counter answers with one of the responder's own plans for the same slot or a new meal, sent as a new offer back (the old one is `countered`). A new offer for the same person, day and slot withdraws the sender's pending one.
- 2026-10-07 · A pending offer ends when its sender eats the meal, moves it to another day or slot, or leaves it. Offers expire when their day ends in the receiver's time zone: they read as expired at once, and the hourly job `offers.expire` writes it down. Only the two people involved see an offer (not a third member); answered, withdrawn and expired offers stay visible for 14 days.
- 2026-10-07 · Push goes out for a new offer and for a counter-offer when the receiver's `push_offers` switch is on, naming the sender and the meal; accepting, declining and withdrawing are in-app only. The badge on the Today tab counts offers waiting for my answer.
- 2026-10-07 · 'Add ingredients to list' before stock exists (M4): missing means not on the list yet, ticked or not. Amounts for the chosen portions are added up per item and written as text ("400 g", "1,5 kg"); list items made this way have origin `recipe`.
- 2026-10-07 · A portion by cooked weight is grams over the recipe's cooked yield times its servings; it needs the cooked yield.
- 2026-10-07 · Extra tools beyond the brief's list, each a thin call to a service: `withdraw_offer`, `set_share`, `set_exact_amounts`, `move_entry`, `add_recipe_to_list`. `send_offer` defaults the receiver to the only other member. `get_household_snapshot` now lists open offers (stock is still to come).

## Stack and architecture

- 2026-10-06 · One `compose.yaml` serves local and production; only `.env` differs (`SITE_ADDRESS=http://localhost` locally, a domain in production so Caddy fetches TLS). (Confirmed)
- 2026-10-06 · Docker images come from Docker Hub under their official names; a host that hits Docker Hub rate limits can set a registry mirror in its daemon config.
- 2026-10-06 · Backend uses synchronous SQLAlchemy with psycopg 3; FastAPI runs sync endpoints in its thread pool. Simpler services and tests; async only where streaming needs it (SSE in M2).
- 2026-10-06 · Python 3.13 in the images (brief: 3.12 or newer); dependencies managed with uv.
- 2026-10-06 · Frontend stays on TypeScript 5.9 because typescript-eslint and openapi-typescript do not support TypeScript 7 yet.
- 2026-10-06 · Router: React Router 8 in data mode (`createBrowserRouter`); i18next with react-i18next.
- 2026-10-06 · API client: `openapi-typescript` generates types from the FastAPI schema, `openapi-fetch` calls it; CI fails when the generated file is stale.
- 2026-10-06 · Caddy serves the built frontend and proxies `/api` and `/mcp` to the app; the frontend is baked into the Caddy image. (M2: the event stream lives at `/api/events`, so no separate `/events` route.)
- 2026-10-06 · Migrations run at app start under a Postgres advisory lock; the worker waits for the app to be healthy and proves its own health with a heartbeat file touched every loop (stale after 60 s).
- 2026-10-06 · Job queue: one `job` table, workers claim with `FOR UPDATE SKIP LOCKED`; recurring jobs are declared in code and enqueued by the worker's scheduler loop.
- 2026-10-06 · Files are stored on the `files` volume behind a `Storage` interface (local disk implementation only).
- 2026-10-06 · Dockerfiles accept an optional `build_ca` build secret for builds behind TLS-intercepting proxies; normal builds ignore it.
- 2026-10-06 · Playwright is pinned to 1.56.1 to match the Chromium build available in the development sandbox; CI installs the matching browser.
- 2026-10-06 · No ACME email in the Caddyfile: Let's Encrypt no longer sends expiry mail and Caddy renews by itself.
- 2026-10-06 · Open Food Facts: product reads via API v3, text search only as an explicit 'search online' action via search.openfoodfacts.org; at most 15 reads and 10 searches per minute per instance (counted in Postgres); found products cached 30 days, misses 1 day. `OFF_CONTACT` sets the User-Agent contact (default `BASE_URL`); `OFF_ENABLED=false` turns lookups off.
- 2026-10-06 · Barcode scanning uses the browser's BarcodeDetector where it exists (Chrome on Android) and otherwise the `barcode-detector` ponyfill with the ZXing wasm served from our own origin (CSP `'wasm-unsafe-eval'`); typing the number always works.
- 2026-10-06 · MCP: the official Python SDK's low-level server, Streamable HTTP, stateless with JSON responses, mounted at `/mcp/<token>`; tools come straight from the registry.
- 2026-10-06 · The end-to-end tests use a small Open Food Facts stub (`scripts/offstub.py`, compose profile `e2e`) so CI never depends on the live service.
- 2026-10-06 · Live sync: every change record also sends a Postgres NOTIFY (delivered on commit, so rolled-back changes never reach a phone). Each app process holds one LISTEN connection and serves server-sent events at `/api/events`; events only name the kind of thing that changed and the app refetches through the normal API, so permissions stay in one place. No Redis.
- 2026-10-06 · The event stream authenticates once with a function-scoped database session (no connection is held while streaming), sends a heartbeat every 15 s and re-checks the session every 60 s. While it is down the list polls every 15 s.
- 2026-10-06 · Offline list: an outbox in localStorage holds changes in order and is sent in batches of at most 200 when the browser is online, on reconnect of the event stream, and every 10 s while changes wait. The list and history are cached in localStorage so a repeat visit shows them at once. A batch the server rejects as malformed (422) is dropped so it cannot block the queue.
- 2026-10-06 · UUIDv7 ids from one process or device always increase (a 12-bit counter covers ids made in the same millisecond), so rows created together keep their order.
- 2026-10-06 · Household, Settings and About load lazily so the first load stays small; Today and the List are in the main bundle for an instant start.
- 2026-10-07 · Dragging uses `@dnd-kit/core` 6.3 (stable; its React rewrite is still 0.x): a handle on each of my meals, drop on the meal it goes before or on an end-of-day zone; pointer (6 px), touch (held 200 ms, so the page still scrolls) and keyboard sensors with translated announcements. The server picks the new time: the middle between the new neighbours, 30 minutes before the first or after the last, and when no minute is free the later meals move on by one.
- 2026-10-07 · The day is one grid in time order: the same meal of both people side by side, a joint meal across both columns, a dash for an anchor meal a person lacks. Households of more than two people get one plain column each, without spanning.
- 2026-10-07 · The plan page shows 14 days and can extend to 31 (today and 30 ahead); entries link to their day. Planning reuses the add screen in plan mode, with a recipes tab (staples first); both of us eating one dish defaults to two portions.
- 2026-10-07 · dnd-kit hands out callback refs named `set…Ref`, which the React refs lint rule mistakes for ref reads; they are renamed on destructuring (`dropHere`, `dragThis`, `gripHere`).

## Security

- 2026-10-06 · Session cookie `mahlzeit_session`: random 32-byte token, stored as SHA-256 hash, HttpOnly, SameSite=Lax, Secure when `BASE_URL` is https, 30-day sliding expiry.
- 2026-10-06 · CSRF: every unsafe request must send header `X-CSRF-Token` equal to the session's token (returned by `/api/auth/me`); login and invite acceptance are protected by SameSite plus an Origin check.
- 2026-10-06 · Login rate limit: 5 failures per email and 20 per IP in 15 minutes, counted in Postgres.
- 2026-10-06 · Passwords: Argon2id with argon2-cffi defaults, minimum 10 characters, no other composition rules.
- 2026-10-06 · Secrets at rest (push subscription keys now, API keys later) use AES-256-GCM with `ENCRYPTION_KEY` from the environment.
- 2026-10-06 · The API returns error codes (`{"code": "...", "detail": ...}`), never user-facing prose; the client translates them.
- 2026-10-06 · Password reset tokens are single use, valid for 1 hour, stored hashed; using one ends all of that user's sessions. At most 3 requests per user per hour.
- 2026-10-06 · Changing the password ends all other sessions of that user and keeps the current one.
- 2026-10-06 · In production the app and worker refuse to start when `ENCRYPTION_KEY`, `BASE_URL`, VAPID or SMTP settings are missing or inconsistent.
- 2026-10-06 · Connector URL: `BASE_URL/mcp/<token>` with a 2×32-byte random token stored as a SHA-256 hash, one active URL per person; creating a new one revokes the old; tokens are redacted from access logs.
- 2026-10-06 · `/mcp` is exempt from the Origin/CSRF checks because it has no cookies; the token is the only credential and acts with the person's own permissions (change records use client `connector`).

## PWA, push and i18n

- 2026-10-06 · Service worker built with vite-plugin-pwa (`injectManifest`), precaching the app shell; push and notification-click handlers live in the same worker.
- 2026-10-06 · The web manifest uses relative URLs, so `BASE_URL` only needs to reach the server-side parts (emails, push, connector metadata).
- 2026-10-06 · Push messages are sent from the worker through the job queue; subscriptions answering 404 or 410 are deleted.
- 2026-10-06 · `VAPID_SUBJECT` is optional: the push contact defaults to `BASE_URL` when it is https (else `mailto:mahlzeit@localhost`), so a freshly generated `.env` starts without edits.
- 2026-10-06 · Locally the site answers on both `localhost` and `127.0.0.1`; with a localhost `BASE_URL`, `127.0.0.1` is also an allowed origin.
- 2026-10-06 · A push subscription belongs to whoever last signed in on that browser; at most 10 devices per user, oldest dropped.
- 2026-10-06 · Offline, the app shows the last signed-in user from localStorage (without the CSRF token) until the server answers; signing out or a 401 clears it.
- 2026-10-06 · Caddy sends `no-cache` for everything except hashed `/assets/*` (immutable, 1 year), so updates arrive on the next open.
- 2026-10-06 · Language default for a new user is the inviter's language, else German; the login screen follows the browser language until someone logs in.
- 2026-10-06 · Hard-coded UI strings are blocked by `eslint-plugin-i18next`; a unit test requires identical key sets in de, en and nl.

## Operations

- 2026-10-06 · Backups: `pg_dump` custom format plus a tarball of the files volume, encrypted with `age` to `BACKUP_AGE_RECIPIENT`; run by a `backup` service under the `ops` Compose profile; 14 most recent kept.
- 2026-10-06 · Without `BACKUP_AGE_RECIPIENT` the backup is written unencrypted and the script warns; copying backups off the machine is left to the operator.
- 2026-10-06 · Local M0 verification treats `http://localhost` as the live URL; phone installation is verified after deployment because Android requires HTTPS.
- 2026-10-06 · Installability is checked with Chrome's own `Page.getInstallabilityErrors` in a persistent profile, because Chrome never offers install in incognito contexts.
- 2026-10-06 · `scripts/restore-drill.sh` runs as a separate Compose project (`mahlzeit-drill`, port 8088) with its own volumes, backup directory and throwaway age key, so it can never touch real data. `BACKUP_DIR` is configurable for that reason.
- 2026-10-06 · M1 'one day through Claude chat' is verified locally with an MCP client making the same calls Claude makes (end-to-end test); a real Claude chat needs the public HTTPS deployment and is checked after deploying.
- 2026-10-06 · 'Scan to logged under 20 s' is measured in the end-to-end test from the scan tab to the entry on the day view (system time, typed code); with a phone camera the human part is three taps: scan, confirm label (new products only), log.
- 2026-10-06 · M2 'within 3 seconds' and 'airplane mode syncs cleanly' are verified by `frontend/e2e/list.spec.ts` with two browser contexts against the Compose stack (measured about 0.2 s); the offline phone even reopens the app offline before shopping.
- 2026-10-07 · M3 'offer, counter and accept across two phones' is verified by `frontend/e2e/plan.spec.ts` (two browser contexts: a week of dinners from staple recipes, an offer countered and accepted, shares, Eaten, a drag, a recipe on the list); the push messages are checked by service tests with a fake sender (`tests/service/test_offers.py`), real push after deployment on a phone.
